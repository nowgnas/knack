# Impl Review

구현한 에이전트가 자기 코드를 리뷰하면 구현할 때의 가정을 그대로 공유해 같은 실수를 놓친다.
이 스킬은 **구현 맥락이 없는 리뷰어**에게 결과물만 넘겨 리뷰받는다. 리뷰어는 코드를 수정하지 않는다.
경로는 모두 이 SKILL.md가 있는 디렉터리 기준 상대 경로다.

## 1. 리뷰 범위 확정
| 넘길 것 | 기본값 |
|---|---|
| 변경 범위 | `git diff <base>...HEAD` + 작업 트리 변경. base는 PLAN.md의 기준 커밋, 없으면 기본 브랜치와의 merge-base |
| 기준 문서 | `.design/<slug>/PLAN.md` 또는 `BUGFIX.md`. 없으면(경량·단독 요청) 사용자 요청을 성공 기준 3~5줄로 정리 |
| 완료 게이트 | 고위험이면 `.design/<slug>/GATES.md`, 아니면 "없음" |
| 레퍼런스 기능 | PLAN.md 4절의 경로 |
| 체크리스트 | `references/review-checklist.md`의 **절대 경로** (`knack show ref review-checklist --path`) |

구현 중 고민이나 "이렇게 한 이유"는 넘기지 않는다. 설계 결정은 PLAN.md 8절 결정 이력으로 충분하다.

## 2. 리뷰어 실행
| 환경 | 방법 |
|---|---|
| Claude Code | `impl-reviewer` 서브에이전트에 위임 (모델은 `models.json`의 review 작업) |
| Codex | 새 세션: `codex exec -s read-only -C <레포 루트> $(knack model get review --agent codex --format flags) "<리뷰 프롬프트>"` |
| 둘 다 불가 | 체크리스트로 직접 리뷰하고 결과에 **"독립 리뷰 아님"** 명시 |

리뷰 프롬프트 (값을 채워서 그대로 쓴다):
```
너는 이 레포의 독립 코드 리뷰어다. 파일을 수정하거나 생성하지 말고 읽기와 검증 명령만 실행한다. 빌드와 관련 테스트는 실행해도 된다.
- 리뷰 대상: `git diff <base>...HEAD` 와 작업 트리 변경(`git status`, `git diff`)
- 기준 문서: <PLAN.md 또는 BUGFIX.md 경로> — 성공 기준, 정책 결정, 변경 범위를 기준으로 삼는다
- 완료 게이트: <GATES.md 경로 또는 없음> — 있으면 게이트가 성공 기준을 덮는지, 동작과 무관하게 통과하는 게이트가 없는지 본다
- 레퍼런스 기능: <경로들> — 컨벤션 비교 기준
- 체크리스트: <review-checklist.md 절대 경로> 를 먼저 읽고 항목별로 확인한다
- 구현자의 요약·커밋 메시지는 믿지 말고 성공 기준을 코드·테스트와 한 줄씩 대조한다. 빠진 것과 요청하지 않은 추가를 모두 찾는다
- 🔴·🟠마다 체크리스트의 증명 단계(1~5)를 단다. 동작에 관한 🔴·🟠를 돌려 보지 못했으면 "잠재"로 내리고 판가름할 가장 싼 명령을 "증명 요청"에 쓴다. 성공 기준 누락·정책 불일치·범위 밖 변경처럼 읽어서 확정되는 지적은 증명 2로 확정한다
- 반환: 체크리스트의 출력 형식을 따르고 한국어로 쓴다
```

## 3. 결과 처리 (구현자)
지적마다 처리 결과를 단다: **반영** / **보류**(이유) / **반박**(근거 `path:line`)
- 반영하기 전에 지적이 코드에서 사실인지 확인한다. 리뷰어는 맥락이 없어 틀릴 수 있고, 틀렸으면 반박한다.
- 불명확한 지적이 하나라도 있으면 어떤 것도 반영하기 전에 먼저 확인한다(지적끼리 얽혀 있을 수 있다).
- 한 건씩 반영하고 그때마다 관련 테스트를 돌린다. 동의의 말 대신 무엇을 바꿨는지 쓴다.

### 증명 요청 처리
리뷰어는 읽기 전용이라 대개 증명 2~3에서 멈춘다. 판정은 실제로 돌린 결과로 한다.
- 증명 요청을 모두 돌린 뒤에 반영을 시작한다. 증명 실행은 리뷰 라운드로 세지 않는다.
- 구현자(메인 세션)나 `verifier`가 "증명 요청"의 명령을 커밋된 clean 작업트리에서 돌린다. 운영·공유 자원에 닿는 명령은 돌리지 않고 로컬·컨테이너로 바꿔 돌리며, 바꿨으면 원래 명령과 바꾼 명령을 함께 적는다.
- 결과를 한 줄로 남긴다. 다시 돌릴 수 있어야 증거다:
  `증명:<4|5> · 실행:<main|verifier> · commit:<짧은 sha> · 작업트리:clean · cmd:<명령> · exit:<코드> · 출력:<핵심 줄 또는 로그 위치>`
- 결함 판정 기준대로 결함이 나오면 잠재를 🔴/🟠로 올려 반영한다.
- 반박은 결함 판정 기준의 "결함 아님" 결과가 실제로 나왔을 때만 한다. 명령이 실행 실패했거나, 전제(데이터·설정·입력)를 만들지 못했거나, 작업트리가 dirty였다면 반증이 아니다. 잠재로 남긴다.
- 안전하게 돌릴 명령이 없는 잠재(운영에서만 재현 등)는 근거와 함께 사용자에게 올리고, 사용자 결정을 기록한다.
- 잠재 🔴/🟠가 하나라도 미결이면 머지하지 않는다. 2라운드가 끝나도 미결이면 완료로 보고하지 말고 멈춘 뒤 남은 잠재와 증명 요청을 넘긴다.
- 구현자의 설명이나 "컴파일된다"는 증명이 아니다. 실제 값과 실제 실행 결과만 본다.

| 심각도 | 처리 |
|---|---|
| 🔴 Blocker, 🟠 Major | 반영한다. 설계나 정책을 바꿔야 반영할 수 있으면 멈추고 사용자에게 묻는다 |
| 🟡 Minor, ⚪ Nit | 작고 설계 범위 안이면 반영하고, 아니면 후속 작업으로 넘긴다 |
| ❔ 잠재 🔴/🟠 | 증명 요청을 돌려 승격(반영)하거나 반박한다. 돌릴 수 없으면 사용자 결정 |
| ❔ 질문 | 코드로 답할 수 있으면 답을 적고, 정책 문제면 사용자에게 올린다 |

- 반영한 뒤에는 빌드와 테스트를 다시 돌린다. Blocker를 고쳤으면 고친 부분만 한 번 더 리뷰받는다. **리뷰는 최대 2라운드**.
- 결과는 대화로 보고하고, 계획 파일이 있으면 `PLAN.md` 9절 독립 리뷰 줄(리뷰어·심각도별 건수·반영/보류)을 채운다.
- **고위험일 때만** 지적 전문을 `templates/REVIEW.md` 형식으로 `.design/<slug>/REVIEW.md`에 남긴다. 게이트와 함께 다시 읽히기 때문이다. 그 밖에는 파일을 만들지 않는다 — 지적은 PR 코멘트와 커밋이 보관한다.

## 4. 완료 기준과 보고
완료 = 🔴·🟠가 모두 반영됐거나 사용자 결정으로 보류됐고, 잠재 🔴/🟠가 모두 증명(4 이상)으로 확정·반증됐거나 사용자 결정으로 닫혔으며, 반영 후 검증을 통과했고, 결과가 기록된 상태(계획 파일 9절, 고위험이면 `REVIEW.md`).
보고: 심각도별 건수, 반영·보류·반박한 지적(이유 포함), 증명 기록 줄, 안전 근거와 그 증명 단계, 남은 리스크.
