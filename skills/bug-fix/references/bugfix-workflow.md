# 버그 수정 단계별 절차

bug-fix 스킬의 세부 절차. `knack show ref bugfix-workflow --section <번호>`로 필요한 단계만 읽는다.
수정 계획 게이트, 진행 방식, 완료 기준은 SKILL.md에 있다.

## 1. 증상 정리
- 기대 동작과 실제 동작, 에러 메시지·스택트레이스
- 발생 환경(로컬/개발/운영), 시작 시점, 빈도(항상/간헐), 영향 범위(사용자, 데이터)
- 코드, 로그, git 이력으로 알 수 있는 것은 직접 확인하고 나머지만 질문한다.

## 2. 재현
1. 실패하는 자동 테스트 (단위 테스트가 가능하면 단위, 아니면 통합). 프로젝트의 테스트 스타일을 따른다.
2. 로컬 실행 후 요청 (curl, `.http` 파일)
3. 재현이 안 되면 로그, 데이터, 코드 경로로 발생 조건을 논리적으로 입증하고 "재현 안 됨"을 명시한다.

## 3. 원인 분석
- 스택트레이스에서 가장 깊은 **자기 코드** 프레임부터 본다.
- 여러 컴포넌트를 거치는 문제(API → 서비스 → DB, 프로듀서 → 브로커 → 컨슈머)는 고치기 전에 경계마다 들어오고 나가는 값을 로그·테스트로 확인해 **어느 경계에서 깨지는지** 먼저 찾는다.
- 잘못된 값이 보이는 곳에서 멈추지 않는다. 호출 경로를 거꾸로 따라가 그 값이 처음 만들어진 곳을 찾고, 수정은 그 지점에서 한다.
- 가설 표: 가설 | 근거 | 반증 방법 | 결과(채택/기각). 가설은 한 번에 하나만 세우고 한 가지만 바꿔 확인한다. 틀리면 변경을 되돌리고 새 가설을 세운다(수정을 쌓지 않는다).
- 비슷하게 동작하는 정상 코드와의 차이를 전부 나열한다. "그건 상관없겠지"로 거르지 않는다.
- 회귀가 의심되면 이력을 추적한다.
  ```bash
  git log --oneline --since='2 weeks ago' -- <의심 파일>
  git log -p -S'<심볼>' -- <경로>
  git bisect start <나쁜 커밋> <좋은 커밋> && git bisect run <재현 테스트 명령>
  ```
- 흔한 원인: `knack show ref common-causes --section <분류>`
- 같은 원인이 다른 곳에도 있는지 검색한다(같은 패턴을 복사해 쓴 코드).

## 5. 수정
- 원인 지점을 최소 범위로 고친다. 프로젝트 컨벤션과 `knack show ref readable-code`를 따른다.
- 원인과 무관한 리팩토링은 하지 않는다. 같은 패턴의 다른 발생 지점은 보고한 뒤 결정을 받는다.
- 스키마를 바꿔야 하면 `knack show ref db-migration`을 따른다.
- 수정 시도가 세 번 실패하면 네 번째를 하지 않는다. 고칠 때마다 다른 곳에서 문제가 드러나면 설계·구조 문제일 가능성이 크다. 지금까지의 가설과 결과를 정리해 사용자와 방향을 정한다.
- 데이터 무결성 버그라면, 원인을 고친 뒤 같은 잘못된 값이 다시 들어와도 막히도록 입력 검증·불변식 검사를 한 층 더 둘지 판단한다. 설계 범위를 넘으면 제안만 한다.

## 6. 검증
- 재현 테스트가 실패하다가 통과하는지, 관련 기존 테스트, 빌드, 린트를 확인한다.
- 수정을 잠시 되돌려 재현 테스트가 **다시 실패하는지** 확인하고 복원한다. 되돌려도 통과하는 테스트는 버그를 잡지 못한다.
- 고위험 영역이면 `knack gate run <GATES.md>`로 게이트를 실행하고, 보고 직전에 `knack gate reverify`로 전부 다시 확인한다.
- 재현 테스트는 회귀 방지용으로 남긴다.

## 7. 영향 데이터
- 버그 때문에 잘못 저장된 데이터가 있을 수 있는지 확인한다.
- 있으면 대상을 찾는 조회 쿼리와 보정 스크립트 초안을 만든다. 멱등하게, 건수 확인과 트랜잭션을 포함한다.
- 실행은 사람이 한다. 에이전트는 운영 데이터에 쓰지 않는다.
- 잘못 발행된 이벤트나 이미 실행된 외부 호출이 있었는지도 확인한다.

## 9. 기록
실수의 종류가 분명하면(규모와 무관) 레포의 `docs/mistakes.md`에 `| YYYY-MM-DD | mistake:<slug> | 한 줄 요약 | 버그 기록 |` 한 줄을 추가하고 수정 커밋에 넣는다. 버그 기록은 PR·이슈 링크, 커밋 전이라 없으면 `bug-<slug>`. 파일이 없으면 사용자 확인 후 `../mistake-proofing/templates/mistakes.md`로 만든다(이 스킬 폴더 기준, knack 은 두 스킬을 함께 설치한다). `.design/`와 달리 이 파일은 커밋한다 — 다른 PC·CI에서도 재발 횟수를 세기 위해서다.
경량(1–3개 파일, 동작 변경 없음)이면 그 밖의 파일은 만들지 않고 대화로 보고한다.
그 밖에는 `.design`이 없으면 `mkdir -p .design/bug-<slug> && printf '*\n' > .design/.gitignore`를 먼저 실행하고,
`BUGFIX.md` 템플릿을 채워 저장한다 — 수정 계획과 결과를 같은 파일에 쓰고 요약 파일을 따로 만들지 않는다.
