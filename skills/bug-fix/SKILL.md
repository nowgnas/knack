# Bug Fix

원인을 입증하기 전에는 고치지 않는다. 증상만 가리는 수정(널 체크, 예외 삼키기, 재시도 추가)은 그것이 실제 원인에 대한 해법일 때만 한다.
단계별 세부 절차: `knack show ref bugfix-workflow --section <번호>`. 흔한 원인: `knack show ref common-causes --toc`.

## 흐름
1. 증상 정리: 기대/실제 동작, 에러, 환경, 빈도, 영향. 운영 장애가 진행 중이면 완화(롤백, 플래그)를 먼저 제안한다.
2. 재현: 실패하는 자동 테스트를 우선한다. 재현 테스트 추가는 진단이므로 게이트 전에도 하고, 했다고 알린다.
3. 원인 분석: 가설은 한 번에 하나씩 표로 좁히고, 여러 컴포넌트를 거치면 경계마다 증거를 모은다. 회귀면 git 이력·bisect. `path:line`으로 설명되면 확정한다.
4. 수정 계획 게이트 (아래)
5. 수정: 원인 지점을 최소 범위로. `readable-code` 기준, 스키마 변경이면 `db-migration`
6. 검증: 재현 테스트가 실패 → 통과, 수정을 되돌리면 다시 실패. 관련 테스트·빌드·린트. 고위험이면 `knack gate run`
7. 영향 데이터: 잘못 저장된 데이터가 있으면 조회 쿼리와 보정 스크립트 **초안**만 만든다. 실행은 사람이 한다.
8. 리뷰: 경량(1–3개 파일, 동작 변경 없음)이 아니면 `impl-review`
9. 요약: `templates/BUGFIX.md` → `.design/<YYYYMMDD>-bug-<slug>/BUGFIX.md`

## 4. 수정 계획 게이트
원인(근거), 재현 방법, 수정 방향, 영향 범위를 보고한다. 아래 중 하나라도 해당하면 **승인 후** 수정하고, 없으면 보고하고 바로 수정한다.
- 동작이나 정책이 바뀐다 / API 계약이나 DB 스키마가 바뀐다 / 데이터 보정이 필요하다
- 수정 범위가 3개 파일을 넘는다 / 원인을 확정하지 못해 추정으로 수정한다
- 고위험 영역이다(`knack show ref high-risk-gates` 1절). 이때는 `GATES.md`도 함께 승인받는다

정책 판단이 필요하면 `knack show ref policy-checklist`를 쓴다.

## 진행 방식과 완료 기준
- **묻지 않고 한다**: 재현 테스트 작성, 로컬 빌드·테스트 실행과 재실행, 로컬 DB·Testcontainers 사용.
- **멈추고 묻는다**: 게이트 조건에 해당할 때, 수정 시도가 세 번 실패할 때(네 번째 대신 구조 문제로 보고 방향을 정한다), 운영 데이터·환경 접근이 필요할 때.
- **완료** = 재현 테스트 실패 → 통과 + 관련 테스트·빌드·린트 통과 + 데이터 영향 확인 + `BUGFIX.md` 작성. 고위험이면 보고 직전 `knack gate reverify`가 ALL MET(포기가 있으면 인계 보고).
- 보고: 원인 한 줄, 수정(`path:line`), 검증 결과, 데이터 영향, 재발 방지 제안.
