# Trace Flow

방향이 두 개다. 스택별 세부(Spring, .NET): `knack show ref tracing --section <번호>`.

| 방향 | 입력 | 답하는 질문 |
|---|---|---|
| 정방향 | `METHOD /path`, 토픽·큐, 배치 잡, `Class.method` | 이 요청이 무엇을 거쳐 어디에 쓰나 |
| 역방향 | 테이블·컬럼, 토픽·큐, 캐시 키, 설정 키 | 이 자원을 건드리는 코드가 어디 전부인가 |

입력이 모호하면 후보를 찾아 제시하고 고르게 한다. 스키마 변경·데이터 보정 전에는 역방향을 먼저 돌린다.

## 정방향 단계
1. 진입점 찾기: 라우팅 결합 규칙, 설정값으로 된 토픽 이름까지
2. 진입 전 공통 처리: 필터, 인터셉터, AOP, 미들웨어, 검증, 인증
3. 호출 체인: 인터페이스는 실제 구현체와 선택 조건까지
4. 데이터 접근: 실행 쿼리, 대상 테이블, 트랜잭션 경계
5. 부수효과: 외부 호출, 이벤트 발행 시점, 캐시
6. 응답과 실패 경로: 예외 → 상태·에러코드, 롤백·보상

## 역방향 단계
1. 자원 확정: 물리 이름과 코드 이름을 모두 모은다 — 엔티티 매핑, 매퍼 XML, 마이그레이션. 둘이 다른 경우가 많다
2. 접근 지점: **읽기와 쓰기를 나눠** `path:line`. ORM 매핑, 네이티브·동적 SQL, 문자열로 조립한 쿼리, 배치·마이그레이션·운영 스크립트
3. 경로와 경계: 접근 지점마다 진입점까지 거슬러 올라간 호출 경로, 트랜잭션 경계, 동시성·멱등성에 걸리는 지점
4. 누락 가능성: 찾지 못했을 수 있는 경로를 적는다 — 문자열 조립, 리플렉션, 뷰·프로시저·트리거, 다른 레포·외부 시스템의 직접 접근

"전부 찾았다"고 말하려면 4단계가 있어야 한다. 역방향은 없는 것을 증명하는 작업이라, 어디까지 확인했는지 적지 않은 목록은 쓸 수 없다.

## 산출물과 완료 기준
| 방향 | 템플릿 | 위치 |
|---|---|---|
| 정방향 | `templates/FLOW.md` | `.onboarding/flows/<slug>.md` |
| 역방향 | `templates/USAGES.md` | `.onboarding/usages/<slug>.md` |

폴더가 없으면 `mkdir -p .onboarding/flows .onboarding/usages && printf '*\n' > .onboarding/.gitignore`.

완료(정방향) = 여섯 단계 모두에 `path:line` 근거가 있고(확정 못 하면 `(추정)`과 후보), 시퀀스 다이어그램이 있으며, 3줄 요약을 보고한 상태.
완료(역방향) = 읽기·쓰기가 나뉘어 있고, 항목마다 `path:line`과 호출 경로가 있고, 누락 가능성과 확인 범위가 적혀 있는 상태.
추적은 비즈니스 로직까지만 하고 프레임워크·라이브러리 내부로는 들어가지 않는다.
