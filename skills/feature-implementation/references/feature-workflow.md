# 기능 구현 단계별 절차

feature-implementation 스킬의 세부 절차. `knack show ref feature-workflow --section <번호>`로 필요한 단계만 읽는다.
게이트(5단계), 승인 후 진행 방식, 완료 기준은 SKILL.md에 있다.

## 작업 폴더 (표준 규모에서만)
```bash
mkdir -p .design/<slug> && printf '*\n' > .design/.gitignore
```
경량은 파일을 만들지 않는다. `.design/`는 커밋되지 않는다. 팀이 설계 문서를 커밋하는 관례(`docs/design/` 등)가 있으면 위치를 사용자에게 묻는다.
폴더 이름에 날짜를 넣지 않는다 — 같은 기능을 다시 손댈 때 이 파일을 찾아 고쳐 쓰기 위해서다.

## 1. 요구사항 정리
- 요청을 한 문단으로 다시 서술하고 **목표**와 **비목표**(이번에 하지 않는 것)를 나눈다.
- **성공 기준**: 어떤 입력·상황에서 어떤 결과가 나오면 완료인지, 테스트로 옮길 수 있는 형태로 적는다.
- 참고한 티켓·문서·대화를 기록한다.

## 2. 정책 명확성 점검
`knack show ref policy-checklist`의 영역별로 판정한다. 해당 없는 영역은 생략한다.

| 판정 | 의미 | 필요한 것 |
|---|---|---|
| ✅ 명확 | 요구사항이나 기존 코드에 정해져 있음 | 근거 (요구사항 문장, `path:line`) |
| ❓ 불명확 | 정할 수 없고 결과에 영향을 줌 | 질문 (선택지 + 추천안) |
| ⚠️ 가정 | 합리적 기본값이 있음 | 제안한 기본값, 사용자 확인 |

- 유사 기능에 이미 구현된 규칙(검증, 권한, 상태 전이)은 근거로 쓸 수 있다.
- 새 요구사항이 기존 정책과 **충돌**하면 반드시 ❓로 올린다.

## 3. 코드베이스 맥락 파악
- `.onboarding/ONBOARDING.md`가 있으면 필요한 섹션만 읽는다. 없는데 레포가 낯설면 `repo-onboarding` quick 모드를 제안한다.
- `knack show ref conventions`에 따라 가장 비슷한 기존 기능 1~2개를 레퍼런스로 정하고 패키지 구조, 네이밍, 계층 간 책임, 예외·응답·테스트 방식을 추출한다.
- 영향 범위: 변경할 코드의 호출부, 같은 테이블·토픽·캐시를 쓰는 곳, 깨질 수 있는 기존 테스트.
- 스택별 탐색: `knack show ref java-spring --toc`, `knack show ref dotnet --toc`

## 4. 구현 설계
`PLAN.md` 템플릿(`knack show template PLAN`)을 채운다. 반드시 들어가야 할 것:
- 레퍼런스 기능과 따를 컨벤션
- 변경 파일 목록(신규/수정). 위치는 기존 패키지 구조를 따른다.
- API 계약(요청·응답·에러코드)과 하위 호환성
- 데이터 변경: 스키마, 마이그레이션, 기존 데이터 처리. 스키마가 바뀌면 `knack show ref db-migration`으로 호환성, 배포 순서, 락 영향, 롤백 전략을 적는다.
- 트랜잭션 경계, 동시성·멱등성, 외부 연동 실패 처리
- 테스트 계획 (프로젝트의 테스트 스타일과 계층)과 성공 기준별 검증 명령 — 9절 결과에서 그 명령의 출력을 적는다
- 구현 순서 (각 단계가 컴파일·테스트로 검증 가능하게 작게)
- 의미 있는 대안이 있었다면 선택 이유
- 고위험 변경(`knack show ref high-risk-gates` 1절)이면 `GATES.md`를 함께 쓴다. 성공 기준마다 게이트가 하나 이상 있어야 한다.

## 6. 구현
- `PLAN.md`의 구현 순서대로 작게 진행하고, 단계마다 컴파일과 관련 테스트를 돌린다.
- 진행하면서 7절 체크박스를 끄고, 새로 발견한 할 일은 그 자리에 덧붙인다. 대화가 길어지면 앞 내용은 요약되지만 파일은 남는다 — 진행 상황은 대화를 거슬러 읽지 말고 이 파일에서 확인한다.
- 성공 기준을 검증하는 테스트는 구현보다 먼저 쓰고 **실패하는 것을 확인**한다. 실패 이유는 기능이 없어서여야 한다(오타·설정 오류가 아니라). Java처럼 컴파일이 먼저 깨지면 시그니처만 둔 빈 구현으로 실패를 확인한다.
- 처음부터 통과하는 테스트는 이미 있는 동작을 검사하고 있는 것이다. 테스트를 고친다.
- 레퍼런스 기능과 같은 구조·네이밍·패턴으로 작성한다. 새 라이브러리, 새 패턴, 새 계층이 필요해 보이면 멈추고 묻는다.
- `knack show ref readable-code`를 따른다. 주석은 코드로 표현할 수 없는 "왜"에만 단다.
- 설계에 없는 리팩토링, 이름 변경, 포맷 변경은 하지 않는다. 발견한 문제는 9절 후속 작업에 적는다.
- 구현 중 새로운 정책 질문이나 설계 변경이 생기면 멈추고 확인받은 뒤 `PLAN.md`를 고친다(8절 결정 이력, 달라진 설계는 해당 절에 반영).

## 7. 검증
- 빌드, 테스트(신규 + 영향받는 기존), 프로젝트의 린트·포맷터(spotless, checkstyle, ktlint, `dotnet format` 등)를 실행한다.
- "통과한다"고 쓰기 전에 이번에 실행한 명령의 출력으로 확인한다. 이전 실행 결과나 "통과할 것"은 근거가 아니다.
- 고위험이면 `knack gate run <GATES.md>`로 게이트를 실행하고, 실패한 게이트는 원인을 고친 뒤 다시 실행한다.
- 실패를 숨기지 않는다. 실행하지 못한 검증은 이유와 함께 보고한다.

## 8. 리뷰
1. 셀프 리뷰: 전체 diff를 아래 순서로 다시 읽고 고친다. 한 바퀴를 돌았는데 고칠 것이 나오지 않으면 멈춘다(경량은 4만).
   1. 완성도 — 성공 기준을 전부 구현했는가. 임시 구현, TODO, 비어 있는 분기가 없는가
   2. 도메인 전문가의 눈 — 이 도메인 담당자가 보면 허술한 곳(경계값, 상태 전이, 금액·시간 처리, 에러 응답)
   3. 결함 사냥 — 정확성, 트랜잭션·동시성, 연동 실패, 성능(N+1, 대량 조회), 테스트가 실제로 동작을 검증하는지
   4. 정리 — 디버그 코드, 사용하지 않는 코드, 불필요한 주석, 설계 밖 변경을 걷어낸다
2. 독립 리뷰: `impl-review` 스킬로 구현 맥락이 없는 리뷰어에게 리뷰받는다. 고위험이면 `GATES.md`도 넘긴다. 🔴·🟠 지적은 반영하고 7단계 검증을 다시 실행한다. 반영하려면 설계나 정책을 바꿔야 하면 멈추고 묻는다.

## 9. 결과 기록과 보고
표준이면 `PLAN.md` 9절(결과)을 채운다. 별도 요약 파일은 만들지 않는다. 대화에는 다음을 보고한다.
- 무엇을 구현했는지 (3줄 이내)
- 핵심 변경 (`path:line` + 한 줄 설명)
- 주요 결정과 설계 대비 달라진 점
- 검증 결과 (실행한 명령과 결과, 실행하지 못한 것)
- 고위험이면 보고 직전 `knack gate reverify` 결과와 포기한 게이트·인계 대상
- 독립 리뷰 결과 (반영한 지적, 보류한 지적과 이유)
- 리뷰어가 집중해서 볼 곳, 후속 작업
