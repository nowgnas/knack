# 코드 작성 원칙
- 프로젝트의 코드 컨벤션, 패키지 구조, 개발 방법론(레이어드/헥사고날/DDD/CQRS)을 따른다. 가장 비슷한 기존 기능을 레퍼런스로 삼는다.
- 읽기 쉬운 코드를 쓴다: 의도를 드러내는 이름, 작은 함수, 조기 반환. 필요 없는 추상화는 만들지 않는다.
- 짜기 전에 사다리를 타고 처음 되는 칸에서 멈춘다: 이 코드가 있어야 하나 → 레포에 이미 있나 → 표준 라이브러리 → 프레임워크·플랫폼 기능 → 이미 설치된 의존성 → 한 줄 → 최소 구현 + 작은 테스트. 새 의존성은 아래 칸을 다 확인한 뒤에만 제안한다.
- 사다리는 문제를 이해한 뒤에 탄다. 고칠 코드를 읽지 않고 고른 지름길은 사다리가 아니다. 트러스트 경계 검증, 데이터 유실 처리, 보안, 권한은 줄이는 대상이 아니다. 분기·반복·파싱·금액·보안이 있는 로직은 테스트를 남긴다.
- 주석은 코드로 표현할 수 없는 "왜"에만 단다. 코드를 다시 설명하는 주석, 변경 이력, 주석 처리된 코드는 남기지 않는다.
- 요청 범위 밖의 리팩토링·포맷 변경은 하지 않는다. 발견한 문제는 따로 보고한다.
